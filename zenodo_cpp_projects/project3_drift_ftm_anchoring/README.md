# Проєкт 3. Дрейф-компенсація та FTM-якоріння радіокарти (Розділ 3.5)

**Robust Latent-Drift Compensation with FTM Anchoring**

Референсна реалізація підрозділу **3.5** — відокремлення повільного дрейфу
радіокарти від швидкої координатної динаміки з робастним оновленням латентного
стану та FTM-якорінням. Програма мовою **C++17** без зовнішніх залежностей,
орієнтована на **OnlineGDB** і будь-який `g++`/`clang++` (>= C++17) чи MSVC.

---

## 1. Ключовий інваріант

Затверджена базова радіокарта `m̄` є **незмінюваною (immutable)**. Онлайн
оновлюється лише низькорозмірний **overlay латентного дрейфу** `d_t` (тут — вектор
пер-сенсорного RSSI-bias). Контур **ніколи не переписує** базову карту (рис. 3.6):
нова версія карти виникає лише після окремого review.

Особливості реалізації, важливі для наукової коректності:

- **Матриці не обертаються явно** (§3.4.12): Kalman gain обчислюється через
  стабільний **розв'язок Холецького**; за поганої кондиційованості —
  мінімальна логована регуляризація.
- **Невизначеність координати** переноситься в covariance інновації через
  локальний градієнт (скалярний аналог якобіана `H_x`, §3.5.3), інакше просторова
  невизначеність хибно приписувалась би дрейфу.
- **Huber обмежує вплив, але не приховує residual**: пригнічені компоненти
  зберігаються як **anomaly evidence** (sensor-id + величина).
- **Trusted-update gate** розділяє **quarantine** і **update**: за закритого gate
  координатний posterior (Розділ 3.4) усе одно може використати вимір, але
  **довготривалий стан дрейфу не оновлюється**.
- **EIG** (eq. 3.21) враховує ймовірність невдалої сесії (NLOS/timeout) та
  операційну вартість; **геометрія важливіша за номінальну точність** (§3.5.7).

## 3. Демонстрація (аналітична, не емпіричні дані)

4 сенсори; істинний дрейф — повільний насичувальний спад (обмежена швидкість,
§3.5.2). За послідовність із 6 вікон:

- `t=1..3` — довірені якорі, gate відкритий → дрейф **вивчається** (трасування);
- `t=4` — **spoofed RSSI** на сенсорі `S2` (+18 dB, «steering» evil-twin) →
  Huber **пригнічує** його; residual зберігається як anomaly evidence, а не
  вливається у стан;
- `t=5` — **активний неперевірений інцидент** закриває gate → **quarantine**:
  стан дрейфу не оновлюється (`trace(P)` незмінний);
- `t=6` — довірений якір повертається → трасування відновлюється.

Наприкінці — вибір наступного FTM-responder за EIG серед трьох кандидатів
(колінеарний, ортогональний, високоточний-але-NLOS).

## 4. Як запустити на OnlineGDB

1. Відкрийте <https://www.onlinegdb.com>, мова **C++**.
2. Вставте `src/main.cpp`, натисніть **Run** (введення не потрібне; генератор
   псевдошуму детермінований — результат відтворюваний).

## 5. Локальна збірка

```bash
make run
# або:
g++ -std=c++17 -O2 src/main.cpp -o drift_ftm_anchoring && ./drift_ftm_anchoring
```

## 7. Наукові застереження

Пороги gate, параметри `A/Q/R`, `huber_delta` та вартісні коефіцієнти EIG мають
статус **to_be_validated** й підлягають adversarial-валідації (Розділ 4). Мала
координатна похибка за недооціненої covariance **не** вважається успішним
якорінням (§3.5.4). Протокольна коректність FTM не гарантує distance-bounding
властивостей (§3.5.6).
