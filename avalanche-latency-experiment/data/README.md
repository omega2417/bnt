# `data/`

## `data/raw/` — the campaign dataset

Not tracked in Git: it is regenerated byte for byte from the master seed
(`make pipeline`) and is shipped inside the Zenodo archive. The layout and
every field are documented in `protocol/DATA_DICTIONARY.md`:

```
tx/<run_id>.jsonl.gz        transaction records, one JSON object per line
nodes/<run_id>_blocks.csv   block series: proposal, acceptance, size, interval
nodes/<run_id>_resources.csv  1 Hz CPU, memory, disk p99, queue depth
network/<run_id>_probes.json  RTT/jitter/loss before, during and after the run
manifests/<run_id>.json     run passport: factors, seeds, hashes, provenance
run_index.csv               one row per run
MANIFEST.sha256             hash of every file above
MANIFEST.json               environment, profile, thresholds, provenance
```

## Provenance

Every record carries a `provenance` field. `SIMULATED` means the record came
from the reference model in `alp.simulate` and is **not** a measurement of
the cyber range; `MEASURED` means it came from a real campaign through
`alp.client`. `python -m alp analyze` reads the label from the data and
propagates it into every table, figure and report, and refuses to guess when
a dataset mixes the two.

## Putting real logs here

Drop the campaign's JSONL into `tx/`, the telemetry into `nodes/`, the probes
into `network/` and the passports into `manifests/`, then run:

```bash
make measured
```

Before publishing anything derived from them, complete
`protocol/DATA_REQUIRED.md`.

## What must never appear here

Private keys, internal IP or MAC addresses, account addresses, login names,
or any payload that could identify a person. The client writes a
pseudonymised `account_token`, never a key or an address.
