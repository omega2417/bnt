## Що саме вимірюється

Не інтервал між блоками і не час консенсусної фінальності. Первинна
метрика — **`T_visible`**: час від передавання підписаної транзакції до
першої відповіді *незалежного вузла читання*, що повертає прийнятий
оновлений стан.

```
T_visible,first(i) = min_r t_read(i,r) − t_send(i)          (рів. 5)
```

Операторові потрібен підтверджений стан, а не лише квитанція, тому
вимірювання охоплює повний шлях: подання, поширення між валідаторами,
включення до блока, прийняття, виконання, запис стану та перше підтверджене
читання з вузла, який цей блок не формував.

Кампанія порівнює п'ять профілів формування блоків (штатний, 1000, 750,
500, 250 мс) у трьох топологіях і за п'яти рівнів навантаження, по десять
повторів: **750 прогонів, 34 875 000 запланованих транзакцій, 87,50 год**
мінімального машинного часу.

## Запуск у Google Colab

Увесь конвеєр — розклад, траси, набір даних, статистика, рисунки, звіт,
контрольні суми та архів для Zenodo — виконується у безкоштовному CPU-середовищі
Colab приблизно за хвилину.

**[`notebooks/Avalanche_Latency_Colab.ipynb`](notebooks/Avalanche_Latency_Colab.ipynb)**

Відкрийте ноутбук у Colab і виконайте всі комірки. Він:

1. встановить пакет і виведе арифметику кампанії;
2. згенерує рандомізований розклад і незмінні траси навантаження;
3. сформує еталонний набір даних у точній схемі кампанії;
4. виконає повний статистичний план і побудує всі таблиці та рисунки;
5. перевірить манifest-и SHA-256 і повторно виведе результати, довівши
  побітову відтворюваність;
6. збере архів для депонування в Zenodo й запропонує його завантажити.

У ноутбуці є також комірка **«підключити власні журнали»**: достатньо
вказати каталог із реальними JSONL кампанії, і всі наступні кроки
виконуються без змін.

## Походження даних — прямо

Надані джерела підтверджують фізичну інфраструктуру та задум дослідження.
Вони **не містять сирих журналів, конфігурацій розгорнутої мережі та
фактичних p50/p95/p99.** Тому репозиторій містить:

* повний виконуваний протокол;
* код, який виконуватиме реальну кампанію (`alp.client`, `deploy/`);
* **задокументовану еталонну модель** (`alp.simulate`), що формує набір
  даних у точній схемі кампанії.

Кожен запис, таблиця, рисунок і звіт, побудовані з моделі, мають позначку
`provenance = SIMULATED` та явний банер. **Ці числа не є вимірюваннями
кіберполігона і не можуть подаватися як результати експерименту.**
`protocol/DATA_REQUIRED.md` перелічує, що має надати реальна кампанія;
`protocol/MODEL.md` пояснює, що саме модель відтворює, а що — ні.

Коли реальні журнали з'являться, покладіть їх у `data/raw/tx/` і виконайте
`python -m alp pipeline --skip-simulation --provenance MEASURED`. Більше
нічого змінювати не треба: аналіз ніколи не питає, звідки взявся запис.

## Швидкий старт (локально)

```bash
pip install -r requirements.txt

python -m alp info --profile full        # арифметика кампанії, рів. (1)-(4)
python -m alp pipeline --profile demo    # розклад, набір даних, статистика, звіт
python -m alp verify data/raw results    # перехешування і звірка з манifest-ами
python -m alp reproduce --profile smoke  # повторна генерація і порівняння таблиць
python -m alp package --out dist/avalanche-latency-experiment.zip
```

Профілі кампанії: `full` (попередньо зареєстрований протокол на 750
прогонів), `demo` (усі рівні факторів зі скороченим вікном — типовий для
Colab), `smoke` (двохвилинна кампанія для неперервної інтеграції).

## Ключові рішення дизайну

**Одиниця аналізу — прогін.** Транзакції всередині прогону поділяють блок,
раунд консенсусу й дискову чергу. Bootstrap на окремих транзакціях дав би
штучно вузькі інтервали, тому кожна метрика спочатку зводиться до рівня
прогону.

**Дизайн парний.** Усі конфігурації відтворюють ту саму незмінну трасу в
межах страти `топологія × навантаження × повтор`, тому базову лінію
віднімають попрогонно.

**Один годинник.** Усі часові мітки, що входять до `T_visible`, знімаються
monotonic-годинником генератора, тому міжхостовий зсув не впливає на
первинну метрику. Дисципліну NTP усе одно фіксують — просто їй не потрібно
довіряти.

**Відкритий цикл.** Генератор навантаження не чекає на відповідь перед
наступною транзакцією. Замкнений цикл перетворив би перевантаження на
самообмежувальний потік і приховав саме ту поведінку черг, заради якої
проводиться дослідження.

**Пороги зареєстровано заздалегідь.** Правила стійкості розділу 12 живуть у
`config.py` і застосовуються кодом до перегляду результатів. Максимальне
стійке навантаження подається за обома зареєстрованими правилами;
розбіжність між ними повідомляється як межа, а не приховується.

## Гарантії відтворюваності

* Кожне випадкове значення походить від seed, виведеного з єдиного
  майстер-seed, тому розклад, траси й еталонний набір даних відтворюються
  побайтово.
* `python -m alp reproduce` наново генерує набір даних у тимчасовому дереві
  й порівнює кожен похідний CSV із зафіксованим.
* `MANIFEST.sha256` і `MANIFEST.json` фіксують хеш, середовище, профіль,
  пороги та походження кожного артефакта.
* Архів для Zenodo будується детерміновано: те саме дерево на вході — та
  сама SHA-256 на виході.

## Безпека

Навантаження спрямовується лише на власну дозволену L1 та ізольовані
RPC-точки. Публічна мережа Avalanche ніколи не використовується для високої
інтенсивності. `deploy/preflight.sh` не дозволяє почати прогін, доки існує
маршрут із тестового сегмента до оголошеного виробничого діапазону, а
`deploy/netem.sh` відмовляється формувати затримку на інтерфейсі з
маршрутом за замовчуванням. Приватні ключі передаються через середовище або
сховище секретів і ніколи не потрапляють до JSONL, Git чи відкритого
датасету.
